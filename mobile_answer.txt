## Metadata / Preview — What It Is & Security Reality

---

## What the Preview Actually Does

```
┌─────────────────────────────────────────────────────────────────┐
│                    PREVIEW FLOW (NO DOWNLOAD)                    │
└─────────────────────────────────────────────────────────────────┘

1. Dashboard loads file list from blockchain
   → Shows: filename, size, MIME type (from contract)
   → NO file content, NO CID, NO encryption key

2. User clicks "Preview" on a file
   → Frontend fetches from IPFS gateway (HTTPS)
   → Decrypts in browser memory (AES-256-GCM)
   → Renders in DOM:
      • Image → <img src="blob:">
      • PDF   → <iframe src="blob:"> (PDF.js)
      • Text  → <pre>textContent</pre>

3. User sees content. File NEVER touches:
   • Downloads folder
   • Disk cache (Cache-Control: no-store)
   • localStorage / IndexedDB
   • Service Worker cache

4. On tab close / unload:
   → URL.revokeObjectURL() → blob gone
   → Clear-Site-Data header sent
   → RAM zeroized (WASM memory.fill(0))
```

---

## What Metadata Is Exposed (By Design)

| Metadata | Where | Why |
|----------|-------|-----|
| **Filename** | Contract + Dashboard | User needs to know what they're retrieving |
| **File size** | Contract + Dashboard | User decides if worth retrieving |
| **MIME type** | Contract + Dashboard | Browser needs to render correctly |
| **CID** | Contract (public) | IPFS addressing — content-addressed by design |
| **SHA-256 hash** | Contract (public) | Integrity verification |
| **Timestamp** | Contract (public) | Policy enforcement (time windows) |
| **PIN hash** | Contract (public) | `keccak256(PIN || nonce)` — PIN not stored |

**All metadata is public on-chain.** That's the trade-off for decentralized policy.

## Security Analysis of Preview

| Threat | Preview Mitigation | Residual Risk |
|--------|-------------------|---------------|
| **File content in RAM** | WASM decrypt → zeroize after render | **OS swap/pagefile may persist** |
| **Browser cache** | `Cache-Control: no-store` + `Clear-Site-Data` | **Browser may ignore** |
| **GPU memory (images/PDF)** | `blob:` URLs revoked | **GPU memory not zeroized** |
| **Screenshots/photos** | None | **User can photograph screen** |
| **Forensic tools (Cellebrite)** | No app install, no app data | **Browser artifacts recoverable** |
| **Network sniff (local)** | HTTPS + cert pinning | **MITM blocked if cert valid** |
| **Network sniff (cellular)** | TLS to IPFS gateway | **Carrier sees IP + domain** |

## The Honest Security Claim

| Claim | Truth |
|-------|-------|
| **"Preview leaves no trace"** | **False.** Browser OS may swap RAM, GPU retains textures, screenshots work. |
| **"Preview is safer than download"** | **True.** No file in Downloads folder, no filesystem timestamp, no `Recent Files` registry entry. |
| **"Preview prevents exfiltration"** | **False.** User can screenshot, photo, copy-paste text. |
| **"Preview metadata is minimal"** | **True.** Only what's needed to identify file. No access logs, no user agent, no IP stored. |

---

## What You Tell the Professor

> **"Preview is a *rendering optimization*, not a security boundary. It avoids writing to the filesystem, which eliminates the most obvious forensic artifacts (downloads folder, recent files, filesystem timestamps). But we don't claim it prevents memory forensics, screenshots, or OS-level artifacts. That's impossible on a standard phone OS.  
>   
> The security boundary is the **hardware gate** — the ESP32 decides *whether* the session happens. The preview is just *how* the authorized content is displayed."**

---

## If They Ask: "Why Not Just Encrypt Metadata Too?"

> **"The CID and SHA-256 *are* the integrity proof. They must be public for anyone to verify. Filename/size/type are needed for the receiver to decide *before* authorizing. We could encrypt filename with a per-receiver key, but that adds key management complexity for marginal gain. The threat model assumes the adversary knows *what* files exist — they just can't retrieve them without physical proximity."**
